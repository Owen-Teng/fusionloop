## 原稿定义

> FusionLoop 是一种以可验收业务结果为起点的工作组织原理：每条 Loop 由一位 Loop Owner 承担端到端集成责任，在 Sponsor 授权和人员容量机制内协调人类专家，并按需调用组织上下文、Skill、Agent 和业务系统；常规执行尽可能交给 Agent，关键判断、异常和高风险事项回到 Gatekeeper 或其他有权人员；结果、失败和修复建议经过审核、测试与版本控制后受控写回，成为下一轮工作的起点。

——原稿第 24 页。

Fusion 指人类判断、Agent、组织上下文、方法与系统的融合；Loop 指带有受控学习的循环。

![原图 10：FusionLoop 前后变化](../assets/paper/fusionloop.png)

## 四项变化同时发生

1. **管理单元**：从分段步骤转向完整、可验收结果。
2. **工作承担者**：从只有人执行转向人与 Agent 共同承担。
3. **责任结构**：一位 Owner 守住集成结果，同时保留专业签署、否决与风险责任。
4. **进化机制**：运行证据推动上下文、Skill、Agent、人机分工和制度规则更新，并在下一轮真实工作验证。

## 一条 Loop 的十个要素

| 要素 | 必须说清的问题 |
| --- | --- |
| 触发事件 | 什么情况启动？ |
| 业务结果 | 对谁交付什么完整结果？ |
| Loop Owner | 谁对端到端集成负责？ |
| 输入上下文 | 使用哪些来源、规则、状态、权限和版本？ |
| 人类责任 | 谁判断、承诺、签署和接管？ |
| Agent 执行范围 | 哪些动作获准执行，有什么边界？ |
| 判断门 | 哪些节点必须由有权人员作出决定？ |
| 异常升级 | 超出规则、权限或质量阈值时找谁？ |
| 验收标准 | 谁依据什么证据接受结果？ |
| 结果回写 | 什么经验进入下一轮，由谁审核、测试和发布？ |

## 受控自进化

**真实运行与失败 → 评估问题 → 提出修复 → 有权人员审核与测试 → 发布新版本 → 下一轮验证。**

“自进化”不允许 Agent 无监督修改正式代码、规则、权限或模型。修复建议经过人的判断门、测试、版本发布和再次验证，才成为下一轮的正式能力。失败应保留，不能作为脏数据清掉。

## 与成熟工作方法的关系

传统流程、项目、敏捷团队与 BPM 已有责任、质量和持续改进机制。本文提出的增量是：把 Skill 和 Agent 作为有来源、版本、权限、维护者的正式能力资产；依据结果和失败持续重组人机分工；把工作证据接回岗位、容量、绩效、激励与组织能力。

如果既有 BPM 已具备这些机制，不必为了使用 FusionLoop 名称而重复建设。一般 Agent 工作流只解决执行编排，也不足以自动满足组织制度要求。

## 适用范围

优先选择触发明确、验收成熟、输入可记录、重复交接延误明显、频次足够且可回退的工作。招聘、员工服务、财务、采购、投标、销售运营和客户支持均是可能场景。高信任销售关系、谈判、危机和高风险人事判断仍由人承担关键责任。
