**性质：论文中的制度设计示例，未报告真实实施或业务效果。**

## 结果边界

从有效客户问题或经确认的商机开始，到形成**客户认可、内部可交付，且技术风险、合同承诺和经济性可接受的完整方案**。方案文档写完只是中间产物。

![原图 7：客户解决方案](../assets/paper/customer-solution.png)

| 设计要素 | 原稿安排 |
| --- | --- |
| Loop Owner | 客户解决方案结果负责人，对完整方案集成负责 |
| 调用能力 | 销售与行业洞察、产品、架构、报价、法务、安全、交付和伙伴能力 |
| Agent 任务 | 历史方案检索、需求归纳、草案生成、一致性检查、风险清单、版本管理 |
| 人的判断 | 客户承诺、价格例外、技术可行性、安全合规、合同义务、最终交付承诺 |
| 验收 | 客户认可，同时内部专业与交付条件成立；保留各专业签署与否决 |
| 回写 | 客户异议、失败原因、复用架构、风险模式、交付偏差 |

正式岗位继续保留专业签署和经营责任。方案负责人从文档整合者升级为完整结果负责人；专家经验可沉淀为规则、标准方法和专业 Agent，使专家更多投入例外与重大判断。

## 不把责任无限向后延伸

方案实施、持续采用和经营价值进入后续客户价值 Loop，由相应 Owner 承接。上游约定交接证据与接收者；下游反馈可检验方案质量，但不能把全部后续责任归给方案负责人。

## 转入真实设计时还需补齐

原稿没有给出具体客户、姓名、系统权限、容量额度、数值验收阈值或运行数据。实际使用[十要素画布](../templates/loop-canvas.zh-CN.md)时，应由有权团队填写上下文、Sponsor 授权、异常升级、独立验收者与回退条件，不能把此示例直接当作启动授权。
