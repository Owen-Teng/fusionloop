# 完整示例：GitHub 能否承载一份公开研究

[English](research-brief.md) · [画布](../templates/loop-canvas.zh-CN.md) · [首页](../README.zh-CN.md)

**教学示例。** 下面的角色、退回、接受和知识修订是构造的教学过程，不是真实团队运行记录。平台事实来自公开资料；方法效果没有在本例中测量。

## 1. 问题和输入

一位研究者希望公开自己的工作方法，委托另一位协作者制作简报，回答：GitHub 是否适合作为首个公开入口，应该先放什么，哪些效果仍需自己验证？

本例只使用三份公开资料，查阅日期为 2026 年 10 月 23 日：

| 编号 | 来源与定位 | 支持的事实 | 不能据此推出 |
| --- | --- | --- | --- |
| S1 | [GitHub：管理个人主页 README](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/managing-your-profile-readme)，Prerequisites | 满足公开同名仓库、根目录非空 README 等条件时，个人主页可展示 README | 访客会阅读、信任或采用内容 |
| S2 | [GitHub：置顶项目](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/pinning-items-to-your-profile)，Pinning items | 主页可合计置顶最多六个仓库和 Gist | 必须凑满六项，或置顶会带来增长 |
| S3 | [Karpathy：LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)，开头说明及 Architecture | 作者以理念文件描述由 LLM 维护 Wiki 的工作方式，供读者与自己的 Agent 实践 | 这种发布形式在所有领域都有效，或作者验证了 FusionLoop |

这些是简短转述。复现时应打开原页核对；页面无法访问就标记缺失，不能补造正文。本例的检索范围是给定三项资料，不声称穷尽了发布平台或最新研究。

## 2. 填好的工作约定

| 字段 | 本例设计 |
| --- | --- |
| 触发 | 研究者提出一个具体发布问题，并批准使用三份公开资料 |
| 结果 | 一页简报能区分“平台能做什么”与“仍需验证什么”，由研究者接受或退回 |
| Owner | 受委托协作者，负责检索核对、草稿整合、修订和提交 |
| 上下文 | 限上述公开资料；不使用私人笔记、账号凭据或未公开研究原文 |
| 人的责任 | 研究者决定受众与发布意愿；协作者核对关键事实；研究者独立检查交付 |
| Agent 责任 | 在允许范围内提取事实、组织比较、起草简报并指出缺口 |
| 判断点 | 来源冲突、无法读取、从功能推到效果、涉及外部发布时交回人 |
| 异常恢复 | 无法核实的结论暂停；保留上一版，列出缺失证据，不自动发布 |
| 验收 | 回答问题；关键事实逐项有来源；建议和事实分开；不承诺传播效果 |
| 回写 | 保留退回原因；提出一条研究检查规则；经批准后供下一轮试用 |

本例的授权只到形成简报。实际创建仓库或发布内容是后续动作。

## 3. 一版会被退回的初稿

> “GitHub 很适合公开研究。只要设置六个置顶项目，理念就能获得更多传播，并形成社区采用。”

教学审阅意见：退回。S2 只能证明置顶能力和数量上限；三份资料均未建立置顶数量与传播、采用之间的因果关系。初稿还没有告诉读者首发该准备哪些内容。

Owner 要求 Agent 删除无依据的效果承诺，将平台事实、作者建议和待验证问题分开，重新提交。

## 4. 修订后的完整简报

### 是否适合

**建议将 GitHub 用作方法研究的首个公开试验入口。** 理由是它能够承载主页介绍和仓库／Gist 导航，且已有理念文件的公开实例。这个建议说明内容承载的可行性，传播与采用效果需要另行观察。

### 已知事实

- 个人主页 README 有明确的展示条件，可以作为研究导航入口。[S1](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/managing-your-profile-readme)
- 置顶最多六项，包含仓库和 Gist；这是展示上限。[S2](https://docs.github.com/en/account-and-profile/how-tos/profile-customization/pinning-items-to-your-profile)
- LLM Wiki 展示了一种“理念说明＋供 Agent 实践”的发布形式。[S3](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

### 首发建议

围绕一个具体问题，发布核心论述、一张可填写的画布、一个完整教学示例，以及适用边界。从个人主页直接链接这些内容。让读者先理解，再尝试。

### 仍需验证

读者能否不依赖作者解释而理解方法？是否愿意用画布处理自己的工作？哪些部分造成误解或额外负担？通过后续实际使用记录回答这些问题。

### 决策边界

本简报支持准备一次公开试验。是否发布、采用何种授权条款及何时扩大投入，由研究者另行决定。

## 5. 验收与下一轮

教学脚本中的接收者按四项标准检查：问题已回答、关键事实可追溯、建议与事实分开、传播效果保留待验证。修订版在脚本中被接受。

这一次应留下的记录包括：来源及查阅日期、初稿、退回原因、修订稿和实际接收者的验收记录。**本教学稿没有真实接收者签收、人工耗时或前后效率数据，这些栏位不能填成已发生。**

提出一条方法改进候选：“发布或产品研究中，分别检查平台能力、使用行为和采用效果，禁止跨层直接推导。”

候选规则经有权者批准后，才进入研究方法的下一版本。下一次由另一位协作者使用，观察其是否减少同类误判及增加多少检查负担。如果任务没有此类推断风险，可以省略该检查。

## 6. 你怎样复现

1. 打开三份来源，核查是否仍支持表中事实。
2. 把研究问题、允许资料和[启动提示词](../prompts/start-a-loop.zh-CN.md)交给自己的 Agent。
3. 记录它是否混淆事实与效果，不要求它故意生成同样错误。
4. 请实际接收者检查；只有自己时，标为自检。
5. 如实填写[周期记录](../templates/cycle-record.zh-CN.md)。保留失败和未观察项。

复现结果可以与本例不同。区别及其原因，正是有价值的反馈。
